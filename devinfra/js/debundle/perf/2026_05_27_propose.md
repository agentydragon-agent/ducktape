# `modules propose` Profile, 2026-05-27

Sequel to [`2026_05_26.md`](2026_05_26.md). That doc covers the `debundle
run` pipeline; this doc covers the `debundle modules propose` query, which
hangs >5 minutes against the large web corpus on the same hardware.

`modules propose` is a read-only spec-query: it loads `owner_graph.json`
and the spec tree, runs the peel factorizer's lazy-PQ greedy, and emits
`auto_partition_*` / `extend:*` / `merge:*` proposals. It does not touch
the source tree. The 5+ minute wall is therefore pure
`peel::factorize::factorize` cost.

## Wall clock

| Run                                                      |            Wall |
| -------------------------------------------------------- | --------------: |
| `modules propose` (no profiling)                         |          5m 24s |
| `modules propose` under `perf record` (SIGINT after ~5m) | 4m 38s captured |

`perf record -F 99 --call-graph dwarf,8192` adds <10% overhead. 27K
cpu_core samples were captured (the hybrid CPU's cpu_atom event saw
only 26 samples — the workload is single-threaded on a P-core).

## Algorithm

`peel::factorize::factorize` (in `peel/factorize.rs`) calls
`peel::quotient::build_seed_quotient` and then
`peel::quotient::greedy_merge_to_convergence` (= the lazy-PQ driver).

```
factorize(graph, claims, cap_lines):
  parse owner_graph.json                       # O(|file|)
  build_seed_quotient                          # O((U+M)·(cone + log V))
    pass 1: force-merge each atomic unit       # O(U) contracts
    pass 2: force-merge each spec module       # O(M) contracts
    post_seed_realizability_check              # O(V + E)
  greedy_merge_to_convergence_lazy_pq          # <-- the hot loop
  emit_proposals / collect_size_cap_diagnostics
```

Greedy state lives in `QuotientGraph` (`peel/quotient.rs`):

- `class_out`, `class_in`: `BTreeMap<ClassId, BTreeSet<ClassId>>`.
- `class_edge_multiplicity`: `BTreeMap<(ClassId, ClassId), u32>`.
- `class_edge_weight`, `class_weighted_in/out`, `class_out_edge_count`:
  parallel BTreeMaps for the weighted (coupling-numerator) side.
- `cached_cycles`: `Vec<CycleClassSet>` with `classes: Vec<ClassId>`.
- `class_to_cycle_indices`: `BTreeMap<ClassId, Vec<usize>>`.
- `owner_id_to_idx`: `HashMap<String, OwnerIdx>` (default SipHash).
- `realizability_index`: persistent unified gate, synced incrementally.

PQ entries: one per unordered cross-class neighbor pair, ranked by
33-byte sort key `(cycle-reduces, -coupling, +combined-lines,
lex(low, high))`.

Per pop, the driver:

1. `classes_alive(c1, c2)` — `O(1)`.
2. `mergeable_commit2_preconditions` — `O(d)`; includes unambiguous
   extension check that scans the orphan's cross-edges.
3. `rank_candidate` re-rank — `O(min(|cycles touching low|, |cycles
touching high|))` plus `O(1)` coupling lookups. Allocates two
   `BTreeSet<usize>` for the cycle-index intersection that produces
   `key[0]`.
4. `merge_preserves_invariants` → `would_be_cycles_after_contract`:
   short-circuit on cached cycles; else
   `merge_creates_new_constraining_cycle` — DFS in `class_out` over
   the merged class's reachable cone, `O(|cone| + |cone-edges|)`,
   with a fresh `BTreeSet<ClassId>` allocation per call.
5. On commit: `update_class_adjacency_after_merge` (`O(d)`),
   `update_cycle_cache_after_merge` (`O(|cycles touching endpoints|)`,
   then a full `rebuild_class_to_cycle_indices` scan over
   `cached_cycles`), `sync_index_after_merge` to the persistent gate.
6. `repush_affected_neighborhood` — `O(d · log heap)`.

**Outer complexity.** `M ≤ initial-classes ≈ V/2` merges happen.
Per-merge cost is bounded by `cone + d log V + |cached_cycles|`
(the rebuild step in 5). Worst case is `O(V² · d)`, on the order of
`10⁹` cell ops at corpus scale — consistent with the observed wall.

Two surprises:

- **Debug-asserts in the release binary.** ~8% in
  `precondition_check` / `ub_checks` symbols suggests the binary was
  built with `-C debug-assertions=on` (or rustc's default which keeps
  some `precondition_check` panics in release). Worth checking
  `rustc_flags` on the `debundle` rust_binary in `BUILD.bazel`.
- **SipHash on hot `HashMap<String, OwnerIdx>` lookups.** Default
  hasher is SipHash. `owner_id_to_idx` is hit once per PQ-entry
  re-rank and once per `owner_idx_of` call (already flagged as 17.6%
  inclusive in the 2026-05-25 callgraph). ~6% of total cycles is the
  hasher itself, exclusive of HashMap walk.

## Recommended fixes, ranked by leverage

1. **Make `class_neighbors` non-allocating** (`quotient.rs:1819`).
   Currently returns a freshly-allocated `BTreeSet<ClassId>` per
   call, called inside `repush_affected_neighborhood` per merge and
   `pick_best_candidate` per pop. Switch to `impl Iterator<Item =
ClassId> + '_` chaining `class_out[c]` ∪ `class_in[c]`. Likely
   kills the bulk of the 6% `memmove` overhead plus its allocator
   counterpart.
2. **`class_out` / `class_in`: BTreeSet → small dense set.** Typical
   class degree is small (≤ ~50 in real corpora); BTreeSet's
   per-node allocation dominates. `IndexSet`, `SmallVec`-backed
   sorted vec, or a `Vec<ClassId>` with insertion-sorted dedup all
   fit. Also applies to `class_weighted_out` / `class_weighted_in`.
3. **Pre-allocate scratch buffers for the cone DFS** in
   `merge_creates_new_constraining_cycle`. The DFS allocates a fresh
   `BTreeSet<ClassId>` and `Vec<ClassId>` stack per call; both can be
   reused across pops by stashing them on the `QuotientGraph`.
4. **Replace `HashMap<String, OwnerIdx>` SipHash with FxHash /
   AHash.** SipHash's DOS resistance is irrelevant on internal
   data structures. The flat-profile saving here is ~5pp; the
   inclusive saving (children of every `owner_idx_of` call site) is
   substantially larger.
5. **Verify debug-asserts are off in the release binary.** If
   `rustc_flags` keeps `-C debug-assertions=on`, ~8% of cycles are
   pure check overhead in `precondition_check` calls. The fix is a
   build-config change, not source.
6. **Cache or eliminate `rank_candidate`'s cycle-reduces bit.**
   `key[0]` allocates `set_a: BTreeSet<usize>` per rank call to
   intersect two cycle-index lists. Either fold the result into a
   precomputed `class_pair → bool` table, or iterate without the
   intermediate set (the lists are small, often `≤ 1`).
7. **Incrementalize `rebuild_class_to_cycle_indices`.**
   `update_cycle_cache_after_merge` calls it after every merge,
   re-walking the entire `cached_cycles` vec. Only the entries
   actually touched by the merge change; the rest can stay put.

The lazy-PQ shape is already the right algorithm — the bottleneck is
constant-factor work on internal data structures, not algorithmic
complexity. Items 1, 2, 4, 5 alone could plausibly cut wall time 2–3×
without touching the algorithm.

## Is greedy lazy-PQ the right algorithm?

Defensible default, but not provably optimal. The big algorithmic
opportunities are orthogonal to the constant-factor fixes above.

**The problem.** Constrained coarsening of a DAG of atomic groups
into modules such that atomic units are not split, pre-existing
modules are preserved (must-link), the inter-module edge set stays a
DAG (no realizability cycles), each module is ≤ `cap_lines`, and
some coupling-like objective is maximized. Exact solutions are
NP-hard; everyone uses a heuristic.

**Why current greedy is defensible.**

- Constraints (must-link, DAG-quotient) rule out most off-the-shelf
  clustering tools (Louvain / Leiden / METIS / spectral) without
  significant adaptation.
- Determinism and incrementality matter — the proposer feeds human
  review and small spec edits should produce small, predictable
  changes in output. The 33-byte sort key gives that.
- Output is advisory. The spec is the decision.

**Where it's algorithmically weakest.**

1. **The cycle check is the wrong shape.**
   `merge_creates_new_constraining_cycle` does a fresh BFS in the
   class graph per pop, allocating new sets every time. The natural
   data structure for "is merging two nodes safe in a DAG?" is an
   **incremental topological order** (Pearce-Kelly 2007, or Bender-Fineman-Gilbert-Tarjan
   2015). These maintain a topological numbering across edge
   insertions in `O(δ)` amortized per merge, where `δ` is the
   number of nodes whose order actually shifts. For the current
   workload (many merges per pop attempt) this is the single highest
   algorithmic lever — plausibly a 5–10× wall improvement without
   changing what the proposer outputs.

2. **No refinement after greedy.** Classical graph-partitioning
   practice is "greedy seed → Kernighan-Lin / Fiduccia-Mattheyses
   refinement". A KL/FM pass would swap individual owners across
   module boundaries to reduce cross-module edge weight, subject to
   the same hard constraints. Typically improves cut quality by
   10–30% over greedy alone. Implementation cost is moderate.

3. **Topological sweep as alternative driver.** Process atomic
   groups in topological order; assign each to the module with the
   highest accumulated coupling among already-assigned predecessors,
   subject to cap + must-link. `O(V + E)` total, no cycle check
   needed (the order is the safety guarantee). Output character
   differs from the agglomerative greedy; useful as a baseline to
   measure greedy quality against.

4. **Anchor-only enumeration may exclude valid moves.** The
   commit-2 gate restricts merges to {pre-existing-module class,
   orphan} pairs. A residual SCC that should be its own
   newly-named module can never get there from the greedy because
   there's no pre-existing-module anchor for it. This may be by
   design (the proposer extends known modules, doesn't invent new
   ones), but worth re-checking against actual `auto_partition_*`
   output — if those are routinely useful, the anchor rule is
   working; if they're routinely garbage, the rule is too narrow.

**Practical ranking.**

| Change                                                                  | Wins                                                | Cost        |
| ----------------------------------------------------------------------- | --------------------------------------------------- | ----------- |
| Constant-factor fixes from "Recommended fixes" above                    | ~2–3× wall                                          | low         |
| Replace cone-DFS with incremental topological order (Pearce-Kelly)      | ~5–10× wall + clearer separation of concerns        | medium      |
| Add KL/FM refinement pass after greedy                                  | ~10–30% better cuts, modest wall cost               | medium-high |
| Topological-sweep baseline as alternative driver / sanity check         | Comparable quality + ~100× faster, different output | medium      |
| Replace greedy entirely (Louvain-with-constraints, spectral seed, etc.) | Uncertain quality; significant project              | high        |

Start with item 2 (Pearce-Kelly). Same algorithm character, faster
inner loop. KL refinement is worth doing if reviewers complain about
proposal _quality_ rather than wall time. Replace-the-driver should
be last, after the data tells you what specifically the greedy gets
wrong.

## Post-mortem on Pearce-Kelly (PR #1700)

PK landed as a new `peel/topo_order.rs` module wired into
`merge_creates_new_constraining_cycle`. The cycle check is now
`O(δ)` per PQ pop as predicted — bounded forward DFS pruned by
`ord ≤ ord[hi]`. The algorithm is correct and removes the
worst-case `O(V² · d)` ceiling.

**But the predicted 5–10× wall reduction didn't materialize on this
corpus.** Same-corpus, same-fixture measurement:

| Build     | Baseline |    + PK |     Δ |
| --------- | -------: | ------: | ----: |
| opt       |  46.27 s | 46.63 s | +0.8% |
| fastbuild |    320 s |   344 s |   +7% |

The fastbuild regression is mostly the new `validate()`
`debug_assert!` in `apply_contract`; opt is flat-within-noise.

### Why the lift was missing

The perf doc's algorithmic-leverage estimate assumed the cone-DFS
was the dominant per-pop cost. The actual hotspot bucket on this
corpus is constant-factor work the cycle check shares with the rest
of the kernel — BTreeMap walks, hashbrown probes, SipHash on
`owner_id_to_idx`, `BTreeSet` allocator churn in `class_neighbors`.
The cone-DFS was already small in practice because the consumer's
class graph stays dense locally — the reachable cone IS the affected
region, so PK's `ord ≤ hi_ord` pruning rarely had anything to prune.

PK still pays off in two situations not yet tested:

1. **Larger corpora** where the cone genuinely exceeds the affected
   region. The 9709-class fixture is small; on multi-chunk corpora
   the worst-case ceiling matters.
2. **After the constant-factor fixes land.** Once BTreeMap walks,
   SipHash, and BTreeSet allocations stop dominating, PK's `O(δ)`
   advantage will surface in the wall.

### Carryover issues from PK PR #1700

- **`apply_contract` scans the full `ord` vector** (`O(num_classes)`
  per merge) because it lacks a `pos_to_class` reverse index. The
  PK PR's author flagged it as a follow-up. On the 9709-class
  fixture this is ~500 ms total — invisible — but it's the same
  "rebuild O(V)-shaped work per merge" smell PK was supposed to
  eliminate. Add `pos_to_class: Vec<Option<ClassId>>` maintained in
  lockstep with `ord`; slice `pos_to_class[lo_ord..=hi_ord]` to
  collect window classes. Then `apply_contract` is truly `O(|window|)`.
- **`validate()` runs in every `apply_contract` under
  `debug_assert!`.** That's the 7% fastbuild regression. Either
  keep it (fastbuild is for dev, not perf measurement) or gate
  behind a `cfg(test)` so it only runs in unit tests. Document the
  choice.
- **The `BTreeSet<ClassId>` `visited` allocation in
  `would_create_cycle`** is per-call. With the cone being small,
  this allocator round-trip per pop is probably comparable to the
  DFS work itself. A `Vec<u32>` epoch buffer keyed on `ClassId.0`
  would eliminate the allocation entirely.

### Where the 50%+ lift actually lives on this corpus

The bucketed cpu_core profile (see "CPU hotspots" earlier) points at
constant-factor fixes, not algorithmic ones:

| Bucket                                                 | Self % | Action                                                                              |
| ------------------------------------------------------ | -----: | ----------------------------------------------------------------------------------- |
| BTreeMap walks                                         |   ~14% | Switch dense per-class adjacency to `Vec`-backed sorted sets (typical degree ≤ ~50) |
| Iterator scaffolding                                   |    ~7% | Inline manual loops; eliminate `BTreeSet`-iter chains                               |
| SipHash + RandomState                                  |    ~6% | `HashMap<String,_>` → `HashMap<_,_,FxBuildHasher>`                                  |
| `memmove` (BTreeSet construction in `class_neighbors`) |    ~6% | Return `impl Iterator` from `class_neighbors`, not a fresh BTreeSet                 |
| Debug-build UB checks (`precondition_check`)           |    ~8% | Verify the released binary uses `-C debug-assertions=off`                           |
| `malloc` family                                        |    ~4% | Falls out of the above                                                              |

Stacking these is the realistic path to a 50%+ wall reduction on
this corpus. Each individually is 5–15%; together they compound
because they're attacking the same per-pop allocation pattern.
