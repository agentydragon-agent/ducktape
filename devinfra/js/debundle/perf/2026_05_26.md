# Large Web Corpus Debundle Profile, 2026-05-26 (post-trim-dead-fix)

This profile was captured from a private consumer corpus using the
`debundle_profile_perf` bazel target wired into the consumer's BUILD via
ducktape's `debundle_pipeline_with_profiles`. Private product names,
snapshot identifiers, repository paths, and module names are intentionally
omitted.

The corpus is the same one the previous `2026_05_20_large_web_corpus` report
covered, but profiled against a newer ducktape pin
(`debundle-f461dd3f2de0`). The headline finding is the
`trim_dead_named_specifiers` Children% collapse described below.

## Pin

The profiled debundler is the prebuilt release `debundle-f461dd3f2de0` —
the first release containing the `trim_dead_named_specifiers` fix that
replaced the O(N×M) inner `Iterator::any` scan with a precomputed
`HashSet<&str>` lookup (commit `21bdb8467`, "precompute claimed-syms
HashSet for trim_dead_named_specifiers (O(N\*M) -> O(N+M))").

A comparison profile (`2026-05-26-post-arch-cleanup`) was captured against
`debundle-fa1b1c98b833` — pre-fix, otherwise identical corpus and host —
and is referenced below as "pre-fix" or "prior baseline."

## `trim_dead_named_specifiers` delta

The single most important change vs the prior baseline:

| Profile                       | `trim_dead_named_specifiers` Children% |
| ----------------------------- | -------------------------------------: |
| 2026-05-26 pre-fix (baseline) |                                 12.62% |
| 2026-05-26 post-fix (this)    |                                  0.03% |

Delta: **−12.59 percentage points.** The fix landed cleanly — the
function still appears in the profile, but with the precomputed
`HashSet<&str>` lookup the inner closure cost has collapsed below
sampling noise:

```
0.03%  0.00%  lowering::exports::trim_dead_named_specifiers
0.03%  0.00%  alloc::vec::Vec<T,A>::retain
0.03%  0.00%  std::collections::hash::set::HashSet<T,S>::contains
0.03%  0.00%  hashbrown::map::HashMap<K,V,S,A>::get_inner
```

The `Iterator::any` → `swc_atoms::Atom::as_str` → `hstr::Atom::as_str`
chain that consumed ~7.71% inclusive in the prior profile no longer
appears.

`lower_chunk` lost essentially all of its `trim_dead_named_specifiers`

(0.69%).

The other top symbols all rose 1–2pp in Children%. That is **not**
absolute slowdown — it's the predictable rebasing effect of removing a
12.6pp chunk from the denominator. Their share of the (now smaller)
total grew while their absolute work stayed the same.

## New top hotspot: `write_tree_reports`

`emit_browser_harness` is now the #1 inclusive hotspot at 12.94%
Children%, narrowly ahead of `materialize_logical_chunk` (11.09%). Its
shape is unchanged from the prior baseline:

```
emit_harness::emit_browser_harness
└── artifact::materialize_artifact_scripts (9.64%)
    └── artifact::write_tree_reports (7.76%)
        └── artifact::write_json (3.59%)
            └── serde_json::ser::to_writer_pretty (3.58%)
                └── <DirectoryManifestIndex>::serialize
                    └── <DirectoryBoundarySummary>::serialize (2.79%)
                        └── <Vec<DirectoryDependencyEdgeManifest>>::serialize (2.18%)
                            └── per-edge BTreeMap<String, …>::serialize (1.51%)
```

Almost all of `emit_browser_harness`'s cost is `serde_json`
pretty-printing of two structures: `DirectoryManifestIndex` and the
nested `DirectoryBoundarySummary` (with its inner
`Vec<DirectoryDependencyEdgeManifest>`).

`serialize_str` / `format_escaped_str` together account for ~9.14%
inclusive (4.58% + 4.56%) — every key and string field in the manifest
is being JSON-escaped on the way out. `__memmove_avx` (4.76% inclusive,
4.51% self) is mostly the serde writer's growing output buffer.

## Recommended next perf target

**`artifact::write_tree_reports` JSON serialization of
`DirectoryManifestIndex` / `DirectoryBoundarySummary`.**

Rationale:

1. **Single highest-leverage symbol.** `emit_browser_harness` →
   `write_tree_reports` is 7.76% Children% — the deepest non-trivial
   inclusive cost that lives in our own code (vs SWC codegen and libc
   memmove, which are amortized across many call sites and hard to dent
   in isolation).
2. **`serde_json` pretty-printing dominates.** 3.58% inside
   `to_writer_pretty` plus 2.18% inside the inner
   `DirectoryDependencyEdgeManifest` vec → all of this is wire-format
   policy, not algorithm. We control both the shape and the serializer.
3. **Two concrete cheap wins, in order:**
   1. Switch `to_writer_pretty` → `to_writer` (compact). Pretty-print
      buys nothing for machine-consumed manifests; spectator humans use
      `jq`. Saves per-token whitespace + indentation work across
      millions of nested map entries.
   2. Shrink `DirectoryDependencyEdgeManifest`'s `BTreeMap<String, …>`
      to a `Vec<(SymbolId, …)>` or a parallel `Vec<&str>` index. The
      per-edge inner `BTreeMap::serialize` is 1.51% by itself, and the
      keys are interned symbols on the Rust side that we are explicitly
      stringifying for the wire.
4. **Bigger pickings beyond that.** Once `write_tree_reports` is
   trimmed, the next visible hotspot will be the SWC codegen `emit_with`
   tree (5.61% + 5.46% + 5.16% ≈ 16.2% inclusive when summed, but
   distributed across many tiny entry points — much harder to dent).
   The directory-manifest JSON is by far the cheapest large win.

## What did not change

- **SWC parsing / visit churn** still occupies the long flat tail
  (~10–15% self time when summed across many small symbols, no single
  symbol breaches 2.5% self). Same as the prior baseline.
- **`materialize_logical_chunk` shape** is unchanged: 4.08%
  `compute_stage_one_analysis`, 2.13% `validate_and_emit_reports`, etc.
  — the per-chunk hot-loop train is at steady state.
- **`sweep_unreachable_top_level` (7.02%)** retains its prior shape:
  3.16% `analyze_prune_items` → 2.38% `analyze_chunk` → 1.54%
  `ChunkCodeGraph::build_full`. Same backlog as before.
