# Large Web Corpus Debundle Profile, 2026-05-26

Snapshot of the latest debundle perf profile against a private consumer
corpus. This doc is a living baseline — when the pipeline gets new perf
wins, edit it in place rather than starting a new file.

The current snapshot reflects the cumulative perf wins through release
`debundle-42175b516d0d`:

1. `lowering::exports::trim_dead_named_specifiers` O(N·M) → O(N+M) via
   precomputed `HashSet<&str>` (commit `21dbb8467`).
2. `write_tree_reports` JSON: `to_writer_pretty` → `to_writer` (commit
   `894d435a7`).
3. `DirectoryDependencyEdgeManifest` per-edge `BTreeMap<String, usize>`
   → sorted `Vec<(String, usize)>` (commit `5fdb13353`).
4. `build_directory_dependency_manifests` path-lookup memoization
   (`module_path_dirname`, `directory_ancestors_for_file`) (commit
   `a176f1f2b`).
5. `ModuleBodyFacts` cache upstream of both consumers in `lower_chunk`
   (commit `8593e7c80`).
6. `peel/quotient`: owner-id → `OwnerIdx` HashMap for O(1)
   `owner_idx_of` (commit `3c7b66451`).
7. `vendor`: longest-prefix index for partial-swap import resolver
   (commit `37d26624c`).
8. **`lower_chunk` per-plan loop parallelized via `rayon::par_iter`**
   (commit `951957122`).

The Nix-specific perf-wrapper fix (`edc2a218b`) keeps the profile
action wall-time under ~100s instead of the pre-fix 30-50 min. Capture

- symbolization is no longer the bottleneck for re-profiling.

### Read of the deltas

The big rises (`emit_browser_harness`, `sweep_unreachable_top_level`,
`materialize_artifact_scripts`) are **rebasing**, not regression: their
absolute cycle counts didn't grow, but they're now larger fractions of
the (smaller-after-parallelization) total because `lower_chunk` got
parallelized off the main thread.

The genuine wins:

- **Path-lookup memoization** materialized cleanly:
  `module_path_dirname` 0.51% → 0.08%, `directory_ancestors_for_file`
  0.57% → 0.15%. Their parent `build_directory_dependency_manifests`
  stayed about the same in fractional terms (rebasing effect again).
- **`compute_stage_one_analysis` dropped 1.48pp** — partly from the
  `ModuleBodyFacts` cache routing more work through one entry point,
  partly from rayon shifting the parent's denominator.
- **`materialize_logical_chunk` halved** (8.54% → 3.91%) — same rayon
  reason, but visible.

## What's hot now

### Sequential hotspot #1: `vendor::strip::sweep_unreachable_top_level`

```
sweep_unreachable_top_level                              (13.23%)
└── analyze_prune_items                                  ( 7.28%)
    └── analyze_chunk                                    (significant)
        └── ChunkCodeGraph::build_full                   ( 7.04%)
```

This path is NOT parallelized today. With `lower_chunk` now off the
main thread, `sweep_unreachable_top_level` is the single largest
remaining sequential block. The two-`analyze_chunk` story (Stage A
runs once, vendor strip runs it again on a post-lowering module with
a different `LocalEffectPolicy`) is still here — and now visibly the
biggest sequential cost.

A real dedup would either (a) parallelize vendor strip (rayon over
the per-chunk loop, mirroring the lowering side), or (b) split
`analyze_chunk` into policy-independent + policy-dependent passes and
share the policy-independent results between Stage A and vendor
strip.

### Sequential hotspot #2: `emit_browser_harness` tree

```
emit_browser_harness                                  (18.18%)
└── materialize_artifact_scripts                      (11.18%)
    ├── write_tree_reports                            ( 8.12%)
    │   └── build_directory_dependency_manifests      ( 2.97%)
    └── per-chunk serialization                       (~5pp)
```

`write_tree_reports` is still serial. The micro-opts inside it have
been picked off; the remaining cost is the JSON serialization tree
itself (serde*json escape + writer growth via `__memmove_avx`). The
next cheap win here is the per-edge `Vec<(SymbolId, …)>` form for the
`BTreeMap` consumers that \_aren't* `DirectoryDependencyEdgeManifest`
— check `DirectoryBoundarySummary` and other tree-report types for
similar shapes.

### SWC codegen tree

`emit_with` variants sum to ~30% inclusive across many tiny entry
points. Same shape as prior snapshots — distributed widely; no single
entry breaches 10%. Reducing the _amount_ of code we re-emit (detect
unchanged modules, skip codegen) remains the only large-leverage path.

## Recommended next perf target

**Parallelize `vendor::strip` per-chunk, mirroring the `lower_chunk`
rayon parallelization.** Now that lowering is off the main thread,
`sweep_unreachable_top_level` (13.23%) is the largest sequential
block; it iterates per chunk and the per-chunk work is data-parallel.

Rationale:

1. **Largest sequential bottleneck.** With `lower_chunk` distributed,
   any further wins come from parallelizing the _other_ per-chunk
   passes. `vendor::strip` is the obvious next candidate.
2. **Pattern is known.** `lower_chunk`'s rayon refactor is the template
   — apply the same `par_iter` over the chunk list, fold results back
   in main thread.
3. **Compounds with `analyze_chunk` dedup.** Even without dedup,
   parallelization brings the wall cost down proportionally; combined
   with the dedup later, the win compounds.

Smaller targets after that:

- **Stage A / vendor strip `analyze_chunk` dedup** — already documented;
  needs the split-into-policy-pass refactor.
- **`DirectoryBoundarySummary` BTreeMap → Vec** (mirror what
  `DirectoryDependencyEdgeManifest` got) — should drop a couple more pp
  from `write_tree_reports`.
- **SWC codegen avoidance** — detect unchanged module bodies (e.g.,
  hash + cache the emitted form keyed on AST shape) and skip
  re-emission. Architecturally invasive; defer until other wins exhausted.
