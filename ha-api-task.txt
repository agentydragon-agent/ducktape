OpenAI browsing constraints as of May 2025 (document in README):
  * LLM cannot navigate to URLs unless they're (a) given verbatim in user input,
    (b) search results page links, (b) they are a link in a page it opened.
    This seems to be a security constraint OpenAI places on the model. So
    we cannot e.g. tell the model "take this base URL and then add this query
    parameter" -- the model is perfectly capable of composing the URL, but
    won't be allowed to navigate to it. Ditto with having the model compose
    a URL in Python and navigate to it: won't work.
  * They do not support cookies.
  * Hence the whole UI must consist of basically a link graph that the LLM
    can use just by clicking around. No <input> boxes, no buttons, no forms,
    But this might easily change soon in the future with LLMs getting more
    capable.
  * Navigating to user-written URLs with query parameters seems to also fail.
  * Model probably cannot send specific headers, answer auth challenges, etc.
  * Hence, we have 2 options for auth:
    * Have the model enter the key as part of the path
    * Present information to the model encrypted and have it decrypt it
      on its side with Python tool use (which it can do).
      Unfortunately this does not solve how we'd authenticate the model
      for the purpose of taking actions. (I eventually want to try this,
      with giving the model normal GET links which will -- somewhat abusing
      HTTP -- make things happen.)
    * Have the model answer a basic challenge-response auth challenge and then
      on success redirect it to a session upon passing it.

      e.g.:
        "you have a secret key, compute sha(key || [this long string]),
         what are the last 2 hex digits?"
        (32 options, each leading the model to /challenge/[nonce]/[xx].
         each URL will tell the model if it succeeded or not, invalidate
         the nonce and show a new challenge. and of course log what
         happened in logs)

      If the model answers correctly, we can leave it say 5 minutes to decide
      what to do next. Links we render from this logged-in point will a secret
      "session extension token" - same token for all links within the signed-in
      session. Clicking any link prolongs the session by 5 minutes.
      If session expires, then any GET to a link with that session's link will
      give message saying that the session expired, and give a new challenge.
      If the challenge is passed, it will direct the model to whatever it
      was trying to do with the old link.

      Lke current decryption, make the auth page be **self-describing** - tell
      the model how to compute the right answer assuming it knows the PSK.
  * Have a human admin page that can use any normal HTTP patterns - forms, GET,
    etc.
    Let the human sign in with a password (no username).
    On sign-in, human will be able to view logs of what model sessions recently
    happened, what they did, whether they're still active, etc.
    The human will be able to invalidate any session.
    Human will be able to *mint* and *revoke* model login keys (i.e. those shared
    secrets that models use to authenticate themselves against the server).
    Minting can be by *generating* a new key with a button (and we'll keep in db
    and allow updating: description, time created, time revoked if revoked, time
    revocation scheduled if any). Use standard HTML datetime pickers for those
    datetimes (except time created).
    This will replace the current one global KEY.
    Have human use of their server follow the normal "sign in / have a session
    with a cookie / sign out" pattern you'd use in normal web apps.

  * For human convenience, once human is logged in, allow human to create
    a session just authed but their password and click through the UI as if
    they were the LLM. This is for testing purposes.
